Backend Architecture Design: Phase 31. New Data Models (Schema Design)We introduce the Appointment model and enhance the MedicalRecord model to support clinical categorization.Appointment Collection:id, patientId, providerId, dateTime (ISO String), status (PENDING, CONFIRMED, COMPLETED, CANCELLED), type (FOLLOW_UP, CONSULTATION, EMERGENCY), notes (Pre-visit notes), teleconsultLink (Optional).Enhanced MedicalRecord (Metadata):tags (Array: e.g., "Cardiology", "Lab"), isArchived (Boolean), previewThumbnailUrl (String).2. Appointment Scheduling LogicThe backend must handle availability and prevent double-booking.Conflict Detection: Before saving a new appointment, the service queries the collection for any existing CONFIRMED status within a 30-minute window for that specific providerId.Status Lifecycle:CONFIRMED $\rightarrow$ COMPLETED: Automatically triggers an entry in the Visit History.CANCELLED: Requires a cancellationReason field for audit purposes.3. Secure Record Previewer (Streaming vs. Downloading)To prevent unauthorized local saving of files, the backend acts as a proxy.Streaming Endpoint: Instead of a direct link to a storage bucket (like S3 or local disk), the backend provides a temporary route: /api/records/:id/stream.Buffer Logic: The backend fetches the file, sets the Content-Type (e.g., application/pdf), and streams the bytes directly to the frontend viewer.Access Check: This endpoint must pass through the Phase 2 Consent Middleware to ensure the requester still has permission at the exact moment of viewing.4. Health Timeline Data AggregatorThe "Timeline" is a frontend visualization, but the backend must provide the "Aggregated Feed."Aggregation Pipeline: A single GET request /api/patients/:id/timeline that uses MongoDB's aggregate to combine data from:MedicalRecord (Upload dates)Appointment (Visit dates)AuditLogs (Specific clinical actions)Data Structure: Returns a sorted JSON array of events, each with a type, date, and summary.5.
